# 在岗哨 Presence Beacon

> 把办公室那台闲置的安卓手机，改造成一个只干一件事的终端：**记录每个人这一周在办公室待了多久。**

3–5 个人的小团队用。不用买硬件、不用装 App、不用签纸质考勤。硬件成本 ≈ ¥30（一个充电支架），软件成本 ¥0。

> 📖 **第一次用请看 [使用手册.md](使用手册.md)** —— 里面有照着点的部署步骤、员工入职流程、
> 日常操作、异常处理和故障排查表。这份 README 是原理 + 速查。

## 它长什么样

```
员工手机（浏览器）                    办公室旧安卓机（浏览器全屏）
┌──────────────┐                   ┌────────────────────┐
│  签进         │  ── 扫二维码 ──▶  │   [ ▓▓▓▓▓▓▓▓ ]      │
│  扫码 + 指纹   │                   │   K7M9Q2X4          │
└──────────────┘                   │   扫码后按指纹       │
                                     │   在场 3/5 人        │
                                     └────────────────────┘
```

一次打卡 ≈ 3 秒：到岗 → 解锁自己手机 → 扫终端二维码 → 按指纹 → 大屏亮「张三 已签进 · 本周 18.5h，还差 5.5h」。

**指纹按在员工自己的手机上，不按在那台旧手机上。** 手机的指纹硬件跟设备绑死，旧手机上按指纹只能证明「这台设备被它的主人解锁了」，证明不了谁站在旁边；反过来，员工自己手机的指纹就是最好的身份证明——免费、零维护、零误识。

技术底座是浏览器原生的 **WebAuthn**：指纹/人脸模板只存在员工手机的安全区，服务器收到的只是「验证通过」这个布尔值。

## ⚠️ 部署前必看：一个硬前提

**指纹功能只在 HTTPS（或 localhost）下可用。** 这是浏览器的安全规则，不是本项目的限制。

用 `http://192.168.x.x:8080` 这种局域网地址打开，浏览器会**整个禁用**指纹能力——员工会看到「这个浏览器不支持指纹验证」，而原因其实是地址不是 HTTPS。

所以你有两条路：

| 方案 | 怎么做 | 适合 |
|---|---|---|
| **A. 域名 + HTTPS（推荐）** | 买一个域名（如 `pb.你的公司.com`），用 Caddy 反代到本机，自动签发免费证书 | 长期用、想省心 |
| **B. 局域网 + 自签证书** | 自己签一张证书，手机上信任一次 | 临时用、不想花钱买域名 |

最小配置（方案 A，用 Caddy，**这是唯一需要你照抄的两行**）：

```bash
# 1) 装 Caddy（会自动帮你申请并续期 HTTPS 证书）
#    debian/ubuntu: sudo apt install -y caddy
#    mac:          brew install caddy

# 2) 写一个 Caddyfile，把域名指到本机 8080 端口
cat > /etc/caddy/Caddyfile <<'EOF'
pb.你的公司.com {
    reverse_proxy 127.0.0.1:8080
}
EOF

# 3) 重载 Caddy
sudo systemctl reload caddy
```

然后把 `.env` 里的这两行改成你的域名：

```bash
RP_ID=pb.你的公司.com        # 裸域名，不带 https://、不带端口
APP_ORIGIN=https://pb.你的公司.com   # 和地址栏一字不差，末尾不加 /
```

配错了会有启动自检提醒你，不会等到全员打不了卡才发现。

## 快速开始

### 方式一：Docker（推荐）

```bash
git clone <这个仓库> presence-beacon && cd presence-beacon
cp .env.example .env      # 按上面的说明改 RP_ID / APP_ORIGIN
docker compose up -d
```

打开 `https://你的域名/admin`，用 `data/.admin-password` 里的口令登录。

### 方式二：直接跑 Node

需要 **Node ≥ 22.13**（因为用了内置的 `node:sqlite`）。

```bash
npm install
cp .env.example .env
npm start
```

## 第一次用，按这个顺序

1. **打开管理端**（`/admin`），用 `data/.admin-password` 里的口令登录。
2. **「员工」页 → 添加员工**，填姓名和每周目标小时数（默认 24）。
   系统会生成一对码：
   - **邀请码**（12 位大写字母数字）：员工第一次在自己的手机上登记指纹时输入
   - **员工码**（8 位大写字母数字）：指纹不可用时的兜底通道

   > 大小写不用纠结：员工输小写也能通过（服务端和前端都会统一转成大写）。
3. **「终端」页 → 添加终端**，填名称和位置。
   系统会生成一条终端链接，**只显示这一次**：
   `https://你的域名/terminal.html?tid=…&key=…`
4. **在旧安卓机上打开这条链接**：
   - 浏览器菜单 →「添加到主屏幕」
   - 装一个 kiosk 浏览器（免 root），或用 Chrome 的 `chrome://flags` 锁定全屏
   - 关掉系统自动更新（否则某天早上屏幕会被更新弹窗占满）
   - 插上充电线，屏幕常亮
5. **员工各自在手机上打开** `https://你的域名/`：
   - 选名字 → 输邀请码 → 登记指纹 / Face ID
   - 浏览器菜单 →「添加到主屏幕」（之后跟原生 App 一样）
6. **跑一次完整的进出**：签进 → 离开时再签出一次。**离开时一定要扫第二次**，否则这段时长不会被计算。

> 完整的照做清单、给员工的话术、异常处理见 [使用手册.md](使用手册.md)。

### 员工换了手机 / 清了浏览器缓存怎么办

不用找管理员。员工自己在员工端首页点「**以前激活过？点这里恢复**」，有两条路：

| 方式 | 怎么做 | 强度 |
|---|---|---|
| **用指纹恢复**（推荐） | 填姓名 → 按一次指纹 / Face ID | 强验证，恢复后仍是强设备令牌，可以重新登记指纹 |
| **用员工码恢复** | 填姓名（有重名再加工位）+ 8 位员工码 | 弱验证，恢复后只能用员工码打卡；**不能**用它去注册新的指纹凭证 |

两条路都不会产生任何打卡记录，恢复完照常上班打卡。

> 为什么要分强弱：员工码是「弱验证」通道，如果拿它就能注册指纹凭证，
> 那拿到员工码的人可以在自己手机上注册一个假指纹，长期占坑别人的打卡通道。
> 所以员工码恢复出来的令牌只够打卡用，想重新登记指纹，得用真的按一次指纹。

## 规则怎么算的

| 参数 | 默认值 | 说明 |
|---|---|---|
| 周目标 | 24 小时 | 可按岗位/个人分别设置 |
| 周起始日 | 周一 | |
| 每日封顶 | 12 小时 | 防止连续签到刷时长 |
| 午休扣减 | 自动扣 1 小时 | 单个在岗区间覆盖 12:00–13:00 **≥ 45 分钟**才触发（说明忘了打卡出去吃饭）；最多扣这段时长的一半，短区间不会被整段吃掉 |
| 假期抵扣 | 自动 | 请假 / 法定假日 / 调休从周目标中扣除 |
| 出差 | 单独标记 | 既不计入，也不抵扣 |
| 跨周归属 | 按分钟切分 | 跨周时长分别算进所属周 |
| 未签退兜底 | 12 小时自动截断 | 并标记「待确认」，可手工修正 |
| 二维码有效期 | 45 秒 | 每次都不同，截图重放无效 |
| 时区偏移 | 480 分钟（UTC+8） | 中国 |

「进/出」怎么配对：第 1 次打卡 = 进，第 2 次 = 出，第 3 次 = 进…… 每对「进→出」产生一个在岗区间，所有区间相加 = 在岗时长。空窗（午休、外出）自然不计入。

**手滑连按两次**会被识别为重复，不会多记一条，也不会把在岗区间提前关闭。

## 常用命令

```bash
npm start               # 启动（自动读取 .env）
npm run dev             # 开发模式（改了自动重启）
npm test                # 规则引擎单测
npm run e2e             # 端到端测试（需要服务已启动）
npm run backup          # 数据备份（会先做 WAL checkpoint）
node test/run-all.js    # 全量回归：11 个套件，自己起服务、跑完自动清理
```

健康检查（`secure` 必须是 `true`，否则指纹不可用）：

```bash
curl https://你的域名/api/health
```

### 关于备份

SQLite 跑在 WAL 模式，最近的数据可能还躺在 `presence.db-wal` 里。**直接 `cp data/presence.db` 会丢掉这些数据，而且不报错。**

用 `npm run backup`，它会先做 checkpoint 再复制出完整快照。服务也会每分钟自动 checkpoint 一次，让土办法复制也不至于丢太多。

## 安全设计

| 事项 | 做法 |
|---|---|
| 管理员口令 | 只存 scrypt 哈希，**不进日志**；首次生成写在 `data/.admin-password`（0600） |
| 员工码 / 邀请码 | 员工码只存哈希；邀请码 12 位（60 bit 熵）；两者都有失败锁定 |
| 限流 | 管理员登录 5 次锁 15 分钟；邀请码/员工码 8 次锁 5–10 分钟 |
| 限流键 | 按员工维度，不绑 IP——否则伪造 `X-Forwarded-For` 就能绕过 |
| 终端密钥 | 128 位随机，只存 sha256；明文只在创建/重置时显示一次 |
| 设备令牌 | 首次登记时下发，与员工强绑定；别人的令牌读不到你的数据 |
| 二维码 | 45 秒过期 + 一次性占用（原子 SQL，并发提交只有一个成功） |
| 生物特征 | 只存在员工手机安全区，服务器拿不到原始指纹/人脸 |
| 敏感值 | SQLite 里没有明文口令；CSV 导出会转义 Excel 公式注入 |

**边界说明**：拿到 `presence.db` 文件 ≈ 拿到全部数据（员工姓名、每周时长、打卡时间）。这是本地部署的固有边界，请把数据目录放在有权限控制的机器上。

## 已知限制

- **指纹挡得住代打卡，挡不住「人在办公室但没干活」**——那本来就不是这套系统要解决的。
- **那台旧手机是单点故障**：它没电/离线时谁都打不了卡。所以员工端会明确提示离线，管理端会显示「离线超过 2 小时」，此时走补卡流程。
- **离线补传做不到**：WebAuthn 的挑战必须由服务器签发，服务端不可达时无法完成指纹验证。这是设计上的取舍，不是偷懒——宁可让员工补卡，也不引入一套更弱的离线认证。
  断网时应用**仍能打开**（外壳和上次同步的周报都在本地缓存里），并明确提示「离线，暂时不能打卡」，不会假装一切正常。
- **清掉浏览器缓存等于换了设备**：本地保存的设备令牌会丢。已提供自助恢复入口（见上），不需要管理员介入。
- **断网时打不了卡，但不会「装作一切正常」**：应用外壳和上次同步的周报都在本地缓存里，断网也能打开，
  页面顶部会挂一条橙色提示「离线模式：显示的是最后一次同步的数据，暂时不能打卡」。
- **不要用「连上办公室 WiFi」做判定**，会误伤用手机热点的人。WiFi 只作辅助参考。
- 没有任何打卡系统能防住铁了心要作弊的人。3–5 人团队靠**信任 + 周报透明**比靠技术更现实。
