# 架构说明

> 给要改这个项目的人看的。**不是**使用手册（那在 `使用手册.md`）。
> 讲清楚：代码怎么组织的、数据怎么流动、每个关键决策为什么这么选。

---

## 1. 一句话

一台放在办公室的安卓手机（**终端**）持续显示一个 45 秒有效的二维码；
员工用**自己的手机**扫这个码、按自己的指纹完成打卡；服务端把打卡流水
按一套规则折算成「这一周在办公室待了多久」。

```
   员工手机 (PWA)                     服务端                    旧安卓机 (kiosk)
  ┌──────────────┐            ┌─────────────────┐          ┌────────────────┐
  │ 扫终端二维码  │──①扫码码──▶│ /api/terminal/  │──②发码──▶│ 显示二维码      │
  │ 按自己的指纹  │            │   :id/session    │          │ + 在场人数      │
  │      ↓       │            │                 │          │ + 打卡闪屏      │
  │ WebAuthn 签名│──③验证──▶│ /api/auth/      │◀─④轮询──│ 每 3 秒拉状态   │
  └──────────────┘            │   assert-verify │          └────────────────┘
        │                     │      ↓          │
        │                     │  events 表     │
        │                     │      ↓          │
        │                     │ rules.js 折算   │
        │                     │      ↓          │
        └─────⑤我的周进度─────│ week / days    │
                              └─────────────────┘
                                     │
                              管理端（老板）
```

**没有实时通道**。员工端打卡完立刻拿到结果（同步响应），但员工端**不轮询**——
它只在需要时拉一次 `/api/me`。终端是唯一持续轮询的（3 秒一次）。

## 3. 数据模型

8 张表，都在 `server/db.js` 的 `SCHEMA` 里：

| 表 | 作用 | 关键点 |
|---|---|---|
| `employees` | 员工 | `active` 软删除；`device_token_hash` + `device_strong`；`invite_code` 一次性 |
| `credentials` | WebAuthn 公钥 | 指纹/人脸模板**不在这里**，只在员工手机安全区 |
| `events` | 打卡流水 | 只追加不修改；`verify_method` 记 `webauthn` / `pin` |
| `exceptions` | 请假/出差/补卡/假日 | `status`: pending / approved / rejected |
| `terminals` | 终端 | `secret_hash` 只存哈希；`last_seen` 用来算离线时长 |
| `sessions` | 终端二维码会话 | 45 秒过期 + `used_at` 一次性原子占用 |
| `challenges` | WebAuthn challenge | 5 分钟过期，用完即删 |
| `settings` | 规则参数 | key-value |

（`migrate()` 只补列，不建新表；表结构变更需要在这里改 `SCHEMA`。）

`migrate()` 给老库补新增列，不改已有列——所以升级永远是加列，不会丢数据。

### 事件不可变

`events` 只 INSERT，没有 UPDATE 路径（除了归属修正 `reassignEvent`，它会保留
`original_employee_id` 和 `reassigned_by`）。审计和争议处理靠这个。

## 4. 规则引擎（`server/rules.js`）

**纯函数，不碰数据库，不读时钟（`nowTs` 由调用方传）**。所以能直接单测。

核心入口：

```js
computeAttendance(events, exceptions, options, nowTs) → {
  days:  [{ date, minutes, countedMinutes, segments, lunchDeducted,
            capped, unclosed, travel, adjustments, ... }],
  weeks: [{ weekStart, minutes, targetMinutes, leaveMinutes, travelMinutes,
            adjustmentMinutes, adjustmentCount, ... }],
  config, truncated
}

weekStatus(result, weekStart, targetMinutes, nowTs) → {
  weekStart, minutes, effectiveTargetMinutes, gapMinutes,
  met, status, daysLeft, hasTravel, unclosedDays, ...
}
```

计算流程（`computeAttendance` 内部）：

```
1. 配对进/出          → segments（in→out 成对；多出来的 in 自动闭合）
2. 切成天              → splitByLocalDay（按本地时区跨天切分，跨周也切）
3. 算每天时长          → 原始区间分钟
4. 午休扣减            → 见 §5.3
5. 每日封顶            → 只封「打卡时长」，补卡不参与
6. 补卡                → 直接加到 adjustments，计入 countedMinutes
7. 出差当天            → countedMinutes = 0（不计入也不抵扣）
8. 汇总到周            → leaveMinutes / travelMinutes / adjustmentMinutes 分别累加
```

**关键点**：第 5 步和第 7 步分离得很干净——`minutes`（打卡时长）、
`adjustments`（人工补卡）、`countedMinutes`（真正计入周时长的数）三个字段各司其职。
出差和封顶只动 `minutes`，不动 `adjustments`。

## 5. 关键设计决策

每个决策都记了「为什么」和「放弃了什么」——改代码前先读这里。

### 5.1 指纹按在员工自己手机上，不按在终端上

**结论先说**：**「旧安卓机当公共指纹识别器」在纯浏览器里是可行的**，不是做不到。
下面有实验证据。但我们仍然选了「员工自己手机按指纹」，代价写在最后。

#### 方案 B 怎么做到（已验证）

WebAuthn 的一个特性常被忽略：**同一个认证器（= 那台旧安卓机）可以为不同用户
各注册一个独立的凭证**。打卡时：

```
员工在旧手机上点「打卡」
  → 浏览器弹账户选择器（张三 / 李四 / 王五），或者直接按手指
  → 认证器内部用「手指 ↔ 本机模板」匹配，匹配上哪个就返回哪个凭证
  → 浏览器把 credential ID 交给服务器
  → 服务器查表 → 知道是谁 → 记一次打卡
```

服务器靠 credential ID 反查身份，这一步是干净的。

**实验**（`test/experiment-public-fingerprint.js`，用 CDP 虚拟认证器跑真实链路）：

| 问题 | 结果 |
|---|---|
| Q1 同一台设备能注册几个人的指纹？ | **3 个人全部注册成功**，服务器存了 3 条互不相同的 credential |
| Q2 断言时给出全部凭证 | ✓ 返回了「王五」的凭证 |
| Q3 断言时完全不指定凭证 | ✓ 返回了「王五」——**浏览器自己挑的** |

**不需要写原生 App**，纯 WebAuthn 就够。

#### 那为什么不选方案 B

| 代价 | 说明 |
|---|---|
| **指纹容量是硬上限** | Android 指纹模组通常只存得下 5 个指纹。3–5 人团队刚好卡满，加一个人就放不下。员工自己手机则理论无上限 |
| **录入门槛高** | 现在：员工在自己手机上录，随时随地 1 分钟。方案 B：要在办公室那台公共机器上录，得排队、得解锁设备、得管理员在场。离职/换人还要在这台设备上重录 |
| **生物特征集中在一台公共设备** | 现在模板分散在各自私密手机的安全区，**公共设备上零生物数据**。方案 B 意味着全公司的指纹模板集中在办公室那台机器的 TEE 里——设备丢失、恢复出厂、贴膜式指纹模组被攻破，影响面是全员 |
| **换设备 = 全员重录** | 旧手机恢复出厂或换指纹模组，所有人的指纹绑定一起失效 |
| **Q3 的隐忧** | 浏览器不指定凭证时是**自己挑**一个。真实硬件上「手指 ↔ 模板」的匹配会决定挑中谁，所以逻辑上没错；但一旦匹配错（老旧模组识别率低、贴膜式假指纹），错的就是**别人的身份** |
| **工程量** | 终端端的交互要重做，还要处理各家浏览器的账户选择器差异 |

#### 方案 B 的真实优势

**少一步扫码**——站在门口按一下手指就完事，3 秒变 1 秒。
这是它唯一但确实很大的好处。

#### 现状的代价

扫码这一步省不掉（每 45 秒换一个新码）。

如果哪天「少一步」比「指纹分散在各自手机」更重要，
实验脚本 `test/experiment-public-fingerprint.js` 可以直接复用——
它已经把「一台设备多凭证 → 反查身份」的链路跑通了。

### 5.2 进/出由客户端显式表达意图（`action=in/out`）+ 服务端 30 秒去重窗

**放弃的方案**：纯服务端状态机自动判断「这次是进还是出」（第 1 次 in、第 2 次 out）。

**为什么**：状态机分不清「连按两次签进」和「签进后 10 秒立刻签退」——
后者会被记成「进 → 出」，把整天时长提前关闭成 10 秒。
让客户端明确说「我现在要签进」或「我现在要签退」，语义就干净了。

**去重窗**：`isDuplicateTap(employeeId, now)` 取该员工最后一条事件，
30 秒内的同向操作判为重复直接返回。但 `out` 在紧跟 `in` 时是**合法的一对**，
所以 `legitSignOut = action === 'out' && dup.kind === 'in'` 会被放行。

### 5.3 午休扣减 = `min(扣减时长, 实际覆盖分钟数, 该区间时长的一半)`

**语义**：只有一个在岗区间**本身就盖过了午休时段**（默认 ≥45 分钟）才扣，
这通常意味着「忘了打下班卡」。正常打了下班卡（哪怕只离开 5 分钟），
空窗本身就不计时，不会被重复扣。

**为什么要三个 min**：

```js
Math.min(cfg.lunchDeductionMinutes, overlap, Math.floor(rawMinutes * 0.5))
```

- `lunchDeductionMinutes`（60）：最多扣 1 小时
- `overlap`：不能扣超过实际盖住午休的分钟数
- `rawMinutes * 0.5`：**不能把这整段吃掉**。12:00–12:50 只待了 50 分钟，
  扣满 50 分钟就记成 0 分钟——但人明明在岗 50 分钟。取一半是「至少留一半」的兜底。

**阈值是 `>=` 不是 `>`**。方案页和代码都统一成 `≥ 45 分钟`。

### 5.4 出差当天：既不计入也不抵扣

出差当天即使还在公司打了卡，`countedMinutes` 也置 0；同时出差时长**不从周目标里扣**。
所以「出差 3 天 + 在公司 2 天」不会被误判成未达标。

原始打卡记录仍保留在 `days[].minutes` 里，明细可查。

### 5.5 设备令牌分强/弱

| 来源 | `device_strong` | 能做什么 |
|---|---|---|
| 指纹登记（`register-verify`） | 1 | 打卡、**追加新的生物特征凭证** |
| 指纹断言恢复（`assert-verify`） | 1 | 同上 |
| 姓名+员工码自助恢复（`/api/auth/recover`） | 0 | 只能打卡，**不能追加凭证** |

**为什么**：如果员工码能追加指纹凭证，那拿到员工码的人可以在自己手机上
注册一个假指纹，长期占坑别人的打卡通道（而且看不出来）。
弱令牌把「打卡权」和「身份注册权」拆开。

`register-options` 的判定：

```js
const addOn = emp.device_strong
  && store.verifyDeviceToken(emp.id, body.deviceToken)
  && store.listCredentials(emp.id).length;   // 追加，不是首次
```

### 5.6 员工离职走软删除

`DELETE /api/admin/employees/:id` → `active = 0` + 清凭据 + 清邀请码，
**`events` 保留**。周报里这个人仍在，标为「已离职」。

**为什么**：对账和争议处理需要历史可查。物理删除会让「他上个月到底来了多少小时」
变得无法回答。

### 5.7 离线：兜底显示，不做补传

**放弃的方案**：离线队列，恢复后自动补传。

**为什么做不到**：WebAuthn 的 challenge 必须由服务端签发（防重放），
服务端不可达时根本无法完成指纹验证。任何「离线也能打卡」的方案都意味着引入
一套更弱的离线认证（那才是在制造安全洞）。

**实际做法**：断网时应用外壳和上次同步的周报都从本地缓存渲染，顶部挂橙色横幅
「离线模式：显示的是最后一次同步的数据，暂时不能打卡」——**不装作一切正常**。

### 5.8 限流键按员工维度，不绑 IP

绑 IP 的话，伪造 `X-Forwarded-For` 就能换一个桶继续爆破。
`clientIp()` 默认只信 `req.socket.remoteAddress`，只有显式设 `TRUST_PROXY=1`
才读 XFF。

### 5.9 哈希强度按熵分档

| 东西 | 熵 | 算法 | 原因 |
|---|---|---|---|
| 终端密钥 | 128 bit | sha256 | 终端每 3 秒轮询一次，scrypt 太慢 |
| 管理员口令 | 低 | scrypt (N=16384) | 人类口令，要抗爆破 |
| 员工码 | 低 | scrypt | 同上 |
| 邀请码 | 60 bit | 明文存 | 要能重置、要比对，够长就行 |

## 6. API 一览

### 公共

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 健康检查，含 `secure`（是否 HTTPS）、`rpID`、`configuredOrigins` |
| GET | `/api/bootstrap` | 员工端启动数据：员工列表、规则配置、服务器时间 |
| GET | `/api/me?employeeId=&deviceToken=` | 我的本周状态 + 最近一次事件 + 下一步该签进还是签退 |

### 认证

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/auth/register-options` | 首次登记的 challenge（凭邀请码）；或追加登记的 challenge（凭强设备令牌） |
| POST | `/api/auth/register-verify` | 校验注册响应，签发**强**设备令牌 |
| POST | `/api/auth/assert-options` | 打卡/恢复的断言 challenge |
| POST | `/api/auth/assert-verify` | 校验断言 → 记打卡；`recover:true` 时只换发令牌不记打卡 |
| POST | `/api/auth/recover` | **自助恢复**：姓名 + 工位 + 员工码 → 弱设备令牌 |

### 打卡与例外

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/checkin/pin` | 员工码打卡（弱验证通道），带 `action=in/out` |
| POST | `/api/exceptions` | 提交请假/出差/补卡/假日 |

### 终端

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/terminal/:id/session` | 生成 45 秒二维码会话（需 `x-terminal-key`） |
| GET | `/api/terminal/:id/qr.svg?session=` | 二维码图片 |
| GET | `/api/terminal/:id/state` | 本终端的在场人数、团队合计、最近 10 条事件 |

### 管理

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/admin/login` | 管理员登录 |
| GET | `/api/admin/overview` | 周报 + 员工 + 终端 + 例外，一次拉全 |
| POST | `/api/admin/employees` | 建员工 → 返回邀请码 + 员工码 |
| PATCH | `/api/admin/employees/:id` | 改目标工时 / 软删除 |
| POST | `/api/admin/employees/:id/invite` | 重置邀请码 |
| POST | `/api/admin/terminals` | 建终端 → 返回密钥链接 |
| POST | `/api/admin/terminals/:id/reset-secret` | 重置密钥（旧链接立即失效） |
| PATCH | `/api/admin/terminals/:id` | 停用/启用 |
| PATCH | `/api/admin/exceptions/:id` | 审批通过/驳回 |
| PATCH | `/api/admin/settings` | 改规则参数 |
| GET | `/api/admin/export.csv?week=` | 导出 CSV |
| GET/POST | `/api/admin/report-preview` / `report-push` | 周报文字版预览 / 手动推送 |

所有管理接口要 `x-admin-token` 头，终端接口要 `x-terminal-key` 头。

## 7. 测试

```bash
npm test              # 纯单元测试：规则引擎 + 安全审查 + 方案对表（不需要服务在跑）
node test/run-all.js  # 全量回归：11 个套件，自己起服务跑完清理
npm run doctor        # 部署自检（可带 URL 参数对着线上跑）
```

`run-all.js` 自己 spawn 服务、逐个跑、跑完清理，用独立临时库
（`data/.test-run-*.db`），不污染交付数据。端口是**动态分配**的空闲端口，
不会和本机已有服务或并行的 CI 任务打架。

**为什么 `npm test` 和 `node test/run-all.js` 分开**：
`npm test` 只跑不需要服务在跑的套件，所以 clone 下来直接 `npm test` 就是全绿，
不会出现「一片红但其实是我没起服务」的情况。需要服务的那几个套件放在
`test/suites/` 下，由 `run-all.js` 统一编排。

| 套件 | 数量 | 覆盖 |
|---|---|---|
| `test/rules.test.js` | 22 | 规则引擎纯函数 |
| `test-reports/*.test.js` | 83 | **方案承诺 ↔ 代码实现** 对表（4 个文件） |
| `test/security.test.js` | 31 | 越权、限流、注入、枚举、启动日志泄露 |

### CI

`.github/workflows/ci.yml` 两个 job：

- **回归测试** —— `npm ci` → 装 Playwright Chromium → `node test/run-all.js`
- **Docker 镜像** —— 真的 `docker build`，起容器，`curl /api/health` 探活

第二个 job 存在的理由：Dockerfile 在开发机上没机会验证（大部分人本地没装 Docker），
在 CI 里跑一次才算数。镜像坏了会直接在 PR 上报红。

## 8. 安全边界

**能防的**：代打卡（指纹在本人手机上）、二维码截图重放（45 秒 + 一次性）、
员工枚举（统一错误文案）、暴力破解（限流 + 锁定）、令牌盗用（设备令牌强绑定）、
Excel 公式注入（CSV 转义）。

**防不了的**：

- 拿到 `presence.db` 文件 ≈ 拿到全部数据。本地部署的固有边界。
- 员工把手机借给别人并**替对方按指纹**（物理胁迫）。
- 铁了心要作弊的人（改系统时间、伪造请求）。3–5 人团队靠信任 + 周报透明更现实。
- 终端被人搬走（但重置密钥能让旧链接立刻失效）。

## 9. 扩展指引

**加一条规则**（比如「每周至少来 3 天」）：
1. `server/rules.js` 里加参数和计算
2. `server/db.js` 的 `DEFAULT_SETTINGS` 加默认值
3. `server/index.js` 的 `rulesConfig()` 和 `/api/admin/settings` 加进去
4. `public/admin.js` 的 `SET_FIELDS` 加一项（名字要和文档一字不差）
5. 在 `docs/使用手册.md` 的规则表里加一行
6. 跑 `node test/doc-consistency.js` —— 它会检查你文档有没有跟上

**加一个终端**：管理端「终端」页添加 → 每台终端一条独立链接和密钥。
不要多台设备共用一条链接（泄露了就是全公司都能扫）。

**接别的推送渠道**：`server/index.js` 的 `reportScheduler` + `renderWeekText`。
目前发的是纯文本，钉钉/飞书/企微的 webhook 都能直接吃。
要发富文本或表格，改 `renderWeekText` 的返回结构。

**加一个前端页面**：`public/` 加 `xxx.html` + `xxx.js`，在 `server/index.js` 的静态
路由里加一条（照抄 `terminal.html` 的写法），`public/sw.js` 的 `SHELL` 数组里
也加一条（不然离线打不开）。
